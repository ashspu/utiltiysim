# UtilitySim: online physical-world plan

Decision date: 11 October 2026. Owner: UtilitySim coordinator, Codex chat `01a12759-bb9e-79b1-b1b9-32f0a5864e10`. Greg requested this five-part plan and a new Slack post. He subsequently specified **#vbs-agents only**.

## Product boundary

UtilitySim owns the physical world: fixed preset geography and population sizes, buildings and occupancy, physical equipment/networks, weather and demand, meter condition, physical events and repair outcomes, time/history, and observations. Greg clarified that AMI/AMR/manual mix, reading/transmission behavior, housing age, customer behavior and household finances also belong in the world builder. Classify fields by their modeled effect, not by an old “Operations” heading. Virtual Systems owns enterprise staffing, processing throughput, queues, tariffs, billing/receivables, collections and operational decision policies. Physical visits and effects remain distinct from enterprise assignments and claimed reports. See [WORLD_V2](WORLD_V2.md) and [shell design](CIVIC_ATLAS_SHELL_DESIGN.md).

The old offline Studio wizard mixed these domains. Port its useful controls and guided progression, not its enterprise features or procedural regeneration path. A map template, saved setup, and instantiated simulation are three different records. An online setup is not a running world. Never interpret a static catalog or browser localStorage as a cloud simulation library.

## Delivery order and parallel work

1. **Immediate shell release:** corrected hero/diagram, authenticated Create/Open entry, physical-only online setup and durable draft validation. Do not replace existing local records.
2. **In parallel:** finish Ashtown; prepare the online runtime and hosting decision; audit the complete physical settings catalog; build event/time controls against one accepted local reference; agree the connector fixtures with VS/Ash.
3. **First integrated online slice:** one pinned town → saved setup → real persisted instance → event → advance → restart/resume → observation delivery to VS. Record the exact deployed revisions and limitations.
4. **Expand to 5–6 presets:** repeat the proven mapping pipeline and per-preset gates. Larger templates must not delay the first complete vertical slice.

No workstream should imply another is complete: cloud setup storage is not compute hosting; accepted illustration is not a complete playable preset; successful delivery is not successful billing; a local test is not a production release.
